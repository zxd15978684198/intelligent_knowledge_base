## 1. 数据结构（真实定义，非设计稿）

### 1.1 `Verdict`：三态枚举

`src/pyknora/services/rag/evidence.py:86-96`，`StrEnum`，仅三个值：

| 值 | 语义 | 下游行为 |
| --- | --- | --- |
| `SUPPORTED` | 片段足以支撑问题 | 正常调模型 |
| `INSUFFICIENT` | 依据不足 | **不调模型**，直接拒答文案，`citations=[]` |
| `CONFLICTING` | 片段之间关键事实互相矛盾 | **不调模型**，列出两处 |

### 1.2 `Evidence`：门控的稳定输入契约

`evidence.py:100-132`，`@dataclass(frozen=True, slots=True)`：

| 字段 | 类型 | 说明（来自该 dataclass 的 docstring） |
| --- | --- | --- |
| `chunk_id` | `UUID` | 片段主键 |
| `document_id` | `UUID` | 所属文档 |
| `active_document_version_id` | `UUID` | 该片段所属**当前生效**文档版本；门控不参与计算，但随 supporting 一起交给调用方做等式校验（`:112-118`） |
| `index_version` | `int` | 索引代次（与文档版本是两条轴） |
| `chunk_ordinal` | `int` | 片段序号 |
| `content` | `str` | 片段全文（判定读全文，不读 snippet） |
| `score` | `float` | 召回分（`rrf_score`）——**只观测不判定**（`:123-124`） |
| `page_no` / `page_end_no` | `int \| None` | 页码允许 `None`；门控不读（`:126-132`） |

> 为什么不直接复用 `RetrievedChunk`：判定层是纯函数，评测脚本、离线 runner、chat 三个入口都要能构造，
> 不能反向依赖 HTTP 出参模型（`:103-106`）。

### 1.3 `EvidenceAssessment`：一次门控的结论

`evidence.py:136-175`，`@dataclass(frozen=True, slots=True)`：

| 字段 | 类型 | 三种 verdict 下的含义（`:142-175`） |
| --- | --- | --- |
| `verdict` | `Verdict` | 三态 |
| `supporting_chunk_ids` | `tuple[UUID, ...]` | `SUPPORTED`=满足覆盖判据的**全部**片段（可多条，见 §2.2）；`CONFLICTING`=**必须一起摆出来的矛盾两处**；`INSUFFICIENT`=**恒为空**（`:142-146`） |

| `unsupported_claims` | `tuple[str, ...]` | 缺口：不足时「缺什么」，冲突时「哪条事实有两个值」，支持时为空（`:159-165`） |

`signals` 的键集合是稳定契约，集中在 `_new_signals()`（`evidence.py:802-823`），共 12 个键：

### 2.2 `supporting_chunk_ids` 的收窄策略（本轮的核心缺陷）

#### 现状：收录「所有」覆盖 required_facts 的片段，不排序、不择一

`assess()` 在 `:910-932` 做的事（按当前文件逐行核对）：

```python
supporting: list[_ChunkView] = []
for view in candidates:
    covered, _, _ = _covers(
        view,
        question_anchors=question_anchors,
        question_fragments=question_fragments,
        asked_quantity=asked_quantity,
        facts=facts,
    )
    if covered:
        supporting.append(view)          # :923——所有满足的都进，不 break、不取 top-1
```

`_covers()`（`:739-770`，逻辑在 `:761-770`）返回 `(covered and not missing_facts,
missing_anchors, missing_facts)`，判据按「片段有没有数字锚点」分三支：

1. 问句带数字锚点 → 锚点必须**全被覆盖**（**不额外要求主题命中**，避免误杀，计划 §11 R4）；
2. 问句不带数字但在问数值（`asked_quantity`）→ 主题命中数 ≥ 2 **且**该片段确实含数字锚点
   （EV-02 的机制："相关但不足"要在这里被拦下）；
3. 其余 → 主题命中数 ≥ 2（1 个片段可能是巧合，2 个才开始像同一件事）。

并且最后一条硬条件：`facts`（`required_facts`）**必须全部落在同一片段内**——分开的片段各有一半事实
不算数，因为模型是逐段读的，把两条拼起来的是猜测（`:910-912` 的注释就是这个理由）。

#### 三个直接后果（都有本轮数值）

1. **supporting 可能等于召回全集**：5 条候选若都覆盖锚点，supporting 就是 5 条；
   `select_context_chunks()` 再按 `chat_max_context_chunks`（`settings.py:62`，默认 6）截断
   （`answer.py:105-129`），于是上下文最多 6 条、`citations` 也随之按同样条数逐条生成
   （`api/v1/chat.py:157-169`）。引用准确率的分母因此是「逐条引用」：
   baseline 45 条 / 15 条 answer 样本 = 平均 3.0 条，candidate 44 条 = 2.9 条；
2. **多引一条就多一个扣分点**：审核规则是「引用的 `snippet` 里必须含 `expect_facts`」
   （`eval/run_eval.py:958-959`），5 条里只要有 4 条不含，就记 4 次
   `CITATION_FACT_MISSING`。本轮两侧分别只有 16/45、14/44 条通过
   （`eval/results/compare-20261030.md:42`），失败台账里 `CITATION_FACT_MISSING` 出现 **21 行**
   （同文件 `:69-107`；全文共 22 次，另 1 次在 `:190` 的汇总里）；
3. **不是「最相关的一条」**：`_best_view()`（`:773-799`）只用于生成 `signals` 与 reason，
   **不参与支持集裁剪**。所以「哪条最该被引」这件事在代码里没有答案——这正是可改的点。

#### 与 01/04 的对应关系

- `docs/Day03/01-优化选型.md` 把「supporting 全量 → 上下文 6 条 → 引用被稀释」列为引用准确率
  退化的机制之一（R2）；
- `docs/Day03/04-优化前后对比.md:140` 进一步判：4 条退化里 `exact-02` 的下降含「分母变化」成分
  （45 → 44），不是模型生成变差；
- 无证据拒答从 `0.6667` 掉到 `0.3333`（`:43`）同源：候选策略把更多「主题相近」的片段塞进候选，
  门控在「候选非空、覆盖判据不满足」时仍应回 `INSUFFICIENT`——它确实回了，但候选变多后
  少数样本落到「锚点恰好被覆盖」的支上，于是变成 `SUPPORTED`（`noev-02`/`noev-03`，
  `compare-20261030.md:91-92`）。

#### 可做的收窄（**本轮一行代码都没改**，只登记方向）

| 方向 | 做法 | 代价 |
| --- | --- | --- |
| a. 只取 top-1 | `supporting` 取 `_best_view()` 那一条 | 多片拼答案的题（若将来 gold 补成多片）会漏引 |
| b. 按命中数取前 N | 依 `required_facts` 命中数/锚点覆盖数排序取前 2 | 需要新排序键，`signals` 要加一项 |
| c. 上下文与引用解耦 | 上下文仍 6 条，`citations` 只列覆盖 required_facts 的 | 引用语义变了，必须补 API 用例 |
| d. 阈值参与 | 给 `Evidence.score` 一个下限 | 与「判定不使用分数阈值」的设计前提冲突，要先改设计 |

判据（改之前必须先绿）：`tests/api/test_api_chat.py` 的
`test_chat_citations_are_only_the_gated_supporting_chunks`（`:324`）与
`test_chat_reports_citations_outside_context`（`:446`）——**这两条本轮未执行**（需真 PG）。
在没有 API 级证据前改 supporting，等于把唯一能保证「引用只来自 supporting」的断言关掉。

## 3. 引用校验的三条规则（本文件的核心设计）

### 规则 R1：引用序号必须落在「本次上下文」范围内

- 判越界：`invalid_cited_indices()` `answer.py:137-144`，返回所有 `n` 不满足 `1 <= n <= context_size`

- 出参：`DoneEvent.invalid_citations`（`src/pyknora/schemas/chat.py:93-100` 的字段），由
  `api/v1/chat.py` 的 `_done()`（`:171-210`，越界计算在 `:186`）写入。

判据：`invalid_citations > 0` 即「模型引用了不存在的资料」，必须被记为失败

**证据**：`tests/unit/test_rag_answer.py:110` `test_invalid_cited_indices_flags_out_of_range`

**本轮通过**（断言 `done.invalid_citations == 1`，`test_citations.py:139-143`）。

### 规则 R2：只能引用「判定为支持」的片段

- 上下文构造：`select_context_chunks()` `answer.py:105-129`——先按 `assessment.supporting_chunk_ids`
  过滤，再按 `chat_max_context_chunks`（`settings.py:62`，默认 6）截断（注释 `:118-124` 解释
  「先 filter 再截断」的顺序不能反）；
- `INSUFFICIENT` / `CONFLICTING` 时上下文为空，`stream_answer()` 在门控分支直接 yield 拒答并
  `return`（`answer.py:333-338` / `:339-342`），**不发任何 token、不调模型**；
- 另一层兜底：`SUPPORTED` 但上下文意外为空时同样拒答（`answer.py:348-366`），
  不把空证据喂给模型。

判据：`citations=[]` 与 `status=ABSTAINED` 必须同时成立；只写一个不算通过。

**证据**：`tests/unit/test_rag_answer_gate.py:199` `test_insufficient_refuses_without_any_http_request`、
`:232` `test_no_evidence_refusal_uses_the_no_evidence_wording`、`:419`
