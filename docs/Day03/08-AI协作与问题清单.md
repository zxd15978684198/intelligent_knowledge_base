## 4. 子 agent 并行编排的真实做法

### 4.1 DAG 波次（实际是 4 个并行波 + 2 个串行收尾波）

- 节点表：`docs/plans/Day03_DAG执行路径.md` 的 **23 个任务 T0.1–T6.3**，并行度上限 **4**，关键路径 ≈2.5 人日。
- **G1 四路并行**：T0.2 语料清点 / T1.2 runner / T3.1 契约与开关（合并了 T4.0）/ T4.1 `evidence.py`。
- **G2 三路**：T0.3 建 KB（由 Lead 亲自打 HTTP）/ T3.2 候选配置 / T4.2 `answer.py` 分流。
- **G3 两路**：T1.1 评测集 / T4.3 `chat.py` 接入门控。
- **G4 文档**：一文件一写者，`docs/Day03/01`–`08` 各归一人。
- **G5 回归、G6 演示与收口**：**DAG 图里没有画**，按顺序由 Lead 串行做（回归要独占数据库，演示要独占进程）。任务书说的「6 个波次 G1–G6」与文档不一致——文档只有 4 个并行波，收尾两波是串行的，**以文档为准**。
- 合并案例：T3.1 与 T4.0 写同一批文件（`schemas/query.py`、`schemas/chat.py`、`services/retrieval/{search,rrf}.py`、`core/settings.py`、`api/v1/{query,chat}.py`），拆开并行必撞车，于是合并为单写者节点 TC，一次改完。

### 4.2 文件边界

- 同一时刻**只有一个写者**能碰同一文件；DAG 表里没列的文件，任何子 agent 都不许写（本次写范围被限定为三份文档，就是这个纪律的直接后果）。
- 共用文件（`core/settings.py`、`schemas/*`、`services/retrieval/*`）只归一个节点；所改即所测，别人的单测不会因为共用文件被动到。
- 边界外发现的问题**只登记不修**：例如 `answer.py:19-22` 的过期 docstring、`tests/unit/test_citations.py` 缺口，都留在 Q 表里。

### 4.3 编排纪律：子 agent 只跑 `tests/unit`

- 子 agent 只准 `uv run --frozen pytest -q tests/unit`（纯函数、不需要数据库）；`tests/api`、`tests/integration`、全量一律 **Lead 串行**跑。
- 原因写在 `AGENTS.md` §6：`tests/api` / `tests/integration` 会 `TRUNCATE ... CASCADE`，要拿 `ACCESS EXCLUSIVE`，两个 agent 同时跑就是 `deadlock detected`，表现为「随机某条用例 ERROR」，不是用例的 bug。
- 这条纪律的代价要如实记：本轮 `tests/api/test_api_chat.py`（适配后）、`tests/api/test_api_refusal.py`、`tests/api/test_api_security_safe.py` **一条都没执行**，证据状态只能写「collected、未 executed」，不能写「通过」。

### 4.4 并行下的验收纪律

- 子 agent 报「已经跑绿」必须同时给命令与输出；给不出的一律降级为「未验证」（例：`test_api_security_safe.py` 作者自述只保证 ruff 与 `--collect-only`）。
- 每个波次结束都留一行真实输出（`docs/IMPLEMENTATION_STATUS.md` 与 `eval/results/README.md`），这样后面合并、回滚、复核都有锚点。
