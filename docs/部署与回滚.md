# PyKnora 部署与版本回滚

> 适用对象：本仓库的开发与演示环境（单机 Docker Compose）。
> 生产编排（K8s/多机、蓝绿、灰度）不在本文范围，本文只保证"一套能起来、能退回去"。
>
> 相关文件：`Dockerfile`（api/worker）、`web/Dockerfile`（Next standalone）、
> `docker-compose.yml`、`.dockerignore`、`scripts/rollback.ps1`、`.github/workflows/ci.yml`。

---

## 1. 一次起栈

```powershell
# 起全部，并等到健康（db 与 api/web 都声明了 healthcheck）
docker compose up --build --wait

# 看状态：migrate 必须是 Exited (0)
docker compose ps -a

# 关掉（保留数据卷）
docker compose down

# 连数据一起删：只在确认要重建库时用，卷删了数据就没了
docker compose down -v
```

端口（宿主）与归属：

| 服务 | 宿主端口 | 说明 |
| --- | --- | --- |
| db | 5435 | 故意避开本机既有的 5433/5434；容器内仍是 5432 |
| api | 8010 | FastAPI，`/health` 是健康检查口径 |
| web | 3000 | Next，`/api/*` 由它同源转发到 `http://api:8010` |
| migrate | 无 | 一次性作业，跑完退出 |

`docker compose config --quiet` 是零成本的"编排定义是否自洽"检查，改动 compose 后先跑它。

## 2. 五个服务各自的契约

| 服务 | 启动命令 | 就绪判据 | 挂了会怎样 |
| --- | --- | --- | --- |
| `db` | pgvector/pgvector:pg16 | `pg_isready` | migrate/api/worker 全部不启（`depends_on: service_healthy`） |
| `migrate` | `bash` 循环喂 `migrations/*.sql` | 退出码 0 | api/worker 不启（`service_completed_successfully`） |
| `api` | `uvicorn pyknora.api.main:create_app` | `/health` 200 | web 不启；`/health` 里 `kb_repo: null` 是"按请求构造仓库"，**不是缺陷** |
| `worker` | `python scripts/run_worker.py` | 无 healthcheck（常驻消费） | 上传会一直 `pending`，不是接口坏了 |
| `web` | `node server.js` | `GET /login` 200 | 页面打不开，但后端仍在 |

`migrate` 用 db 镜像而不是 api 镜像，理由是 psql 在 db 镜像里现成、且迁移文件是
`psql` 脚本（`\set`、`:dim`），不能用 asyncpg 直接执行；迁移文件 bind-mount 到
`/migrations`（容器内没有这个路径时 `psql -f` 必然 `No such file`）。

## 3. 本地门禁与 CI 的分工

| 层 | 命令 | 覆盖 | 何时跑 |
| --- | --- | --- | --- |
| 提交前 | `scripts/ci.py --profile commit` | `lock`(uv lock --check) + `lint`(ruff check/format) + `manifest` | `git commit` 自动（`.githooks/pre-commit`，实测 0.1s） |
| 推送前 | `scripts/ci.py --profile default` | 插件面板勾选的前八步：`lock, sync, lint, type, manifest, test, security, build`（实测 54.1s：8 PASS / 1 WARN / 1 SKIP） | `git push` 自动（`.githooks/pre-push`）；`--stage all` 等价 |
| 手动 | `--profile full` | 全 13 阶段：再加 `integration` / `audit` / `container`，`release`/`deploy` 本地 SKIP | 需要时，或发版前 |
| CI | `.github/workflows/ci.yml` | `lint`(+lock) / `unit`(覆盖率 70% 底线) / `security`(advisory 密钥扫描) / `integration`(真 PG + 全部迁移 + 外键断言) / `audit`(pip-audit) / `docker` / `build`(产物) / `release`(仅 tag) | push、PR、tag |

阶段顺序与命名对齐 GateKeeper 插件的 13 阶段 IR；结果是四态 `PASS`/`FAIL`/`WARN`/`SKIP`，
只有 `FAIL` 改退出码（`WARN` = advisory 已知红，`SKIP` = 未配置或只在 CI）。
`--stage all` 现在就是那八步，不再是「lint+test」的历史别名。

两条刻意的取舍：

- `type`（`ty check src`）**在 `default` 里但标 advisory**：当前真实 31 条诊断，先清再接；
  接了却常年红，等于教所有人忽略门禁——所以它打印 `WARN` 与诊断条数，但不拦提交。
- `security`（detect-secrets，即旧文档里的 `secrets` 阶段）**是 advisory（`--report-only`）**：本仓库的开发 DSN
  （`.env.example`）、测试占位 key（`tests/**` 约 30 处）、文档示例凭据会让
  `detect-secrets-hook` 稳定命中约 40 处；而 `detect-secrets scan` 在同一台机器上
  对同一批文件返回 **0 命中**，生成不出 hook 认的 baseline（两边口径不一致，已复现）。
  要把它变成阻断式，二选一：
  1. 逐处加行内标记：`vision_api_key="vision-key",  # pragma: allowlist secret`
  2. 在一台 `detect-secrets scan` 与 hook 口径一致的机器上重建 `.secrets.baseline`
     并 `detect-secrets audit` 逐条确认。
- `audit`（pip-audit，旧文档里错叫 `security`）**不在任何默认 profile**：它要联网比对 OSV，结论随远端变化；
  让网络抖动决定能不能提交是不可接受的。
- **`build`（`uv build --out-dir dist`）是构建产物的唯一产生点**：先清 `dist/`
  再构建（旧 wheel 留着会在构建失败时被后续上传/发布发出去）。CI 的 `build`
  job 上传名为 `dist` 的 artifact，`release` job **下载**它而不是重新构建——
  两次构建会产出哈希不同的 wheel，attestation 与 Release 就对不上。
  本地要复现：`uv run python scripts/ci.py --stage build` → `dist/` 下出现
  `pyknora-<ver>-py3-none-any.whl` 与 `pyknora-<ver>.tar.gz`。
  `dist/` 在 `.gitignore` 第 5 行，**永远不进版本库**。

## 4. 版本回滚

### 4.1 先想清楚要回什么

回滚不是一个动作，是五个面，**能回的和不能回的完全不同**：

| 面 | 能不能回 | 怎么回 |
| --- | --- | --- |
| 代码/镜像 | 能 | 切镜像 tag（本脚本） |
| 数据库迁移 | **不能**（只追加，无 down） | 只能向前修复，或让旧代码兼容新库 |
| 索引版本 | 能 | 改 `documents.active_index_version_id` 指回旧 build；不删 build |
| 配置（`.env`） | 能 | 还原旧值；模型名/地址改动会让回滚后直接 404 |
| 游标/缓存 | 部分 | 密钥或分页格式变了，旧 `cursor` 会 `CURSOR_EXPIRED`，重新拉一页即可 |

**顺序**：先确认旧代码能读新库 → 再切镜像 → 最后探活。反过来做，等于用旧代码撞新表结构。

### 4.2 用脚本回滚

```powershell
# 只看计划，不动任何东西（推荐先跑这个）
pwsh -File scripts/rollback.ps1 -ToImageTag v1.2.0 -DryRun

# 真的切（api/worker/web 一起）
pwsh -File scripts/rollback.ps1 -ToImageTag v1.2.0

# 只退前端
pwsh -File scripts/rollback.ps1 -ToImageTag v1.2.0 -Services web
```

脚本会：预检 `compose config` 与目标镜像是否存在 → 把当前镜像 ID / 容器 ID / `.env` 的 sha256
写进 `.tmp_ref/rollback-<时间戳>.json` → `docker compose up -d --no-deps --force-recreate`
→ 等 healthy 并探 `/health` 与 `/openapi.json` → 非零退出即代表"回滚没成功"。

它**故意不做**：不动数据卷、不跑 `down -v`、不改迁移、不删备份、不替你下载镜像。

### 4.3 手工回滚（脚本不可用时）

```powershell
# 1) 记录现场
docker compose ps -a
docker inspect --format '{{.Config.Image}} {{.Image}}' $(docker compose ps -q api)

# 2) 切 tag（compose 用 PYKNORA_IMAGE_TAG 变量）
$env:PYKNORA_IMAGE_TAG = 'v1.2.0'
docker compose up -d --no-deps --force-recreate api worker web

# 3) 探活
curl.exe -s http://127.0.0.1:8010/health
```

前提：`v1.2.0` 的镜像已经在本地（`docker image ls | Select-String pyknora`）。
镜像没留就回不去——**发布时给镜像打不可变 tag（git sha 或语义版本），不要只用 `latest`**。

### 4.4 回滚后必须检查的三件事

```powershell
# 1) 索引版本指针：最近激活的 build 是否仍是回滚前那个
docker compose exec db psql -U postgres -d pyknora -c `
  "SELECT id, status, activated_at FROM index_builds ORDER BY activated_at DESC LIMIT 5;"

# 2) 上传链路是否恢复（worker 在跑，作业能从 pending 走到 succeeded）
docker compose logs --tail 50 worker

# 3) 对话上游是否仍可用（模型名是最常见的回滚事故点）
curl.exe -s http://127.0.0.1:8010/health
```

## 5. 已知限制

1. **回滚无自动降级**：compose 没有蓝绿/灰度，回滚是"停旧起新"，会有几秒不可用。
2. **迁移无 down**：这是有意的（AGENTS.md I4）。要回退表结构只能写新的前向迁移。
3. **web 的代理目标在构建期固化**：`rewrites()` 在 `next build` 时求值，`API_PROXY_TARGET`
   是 build arg；运行期改环境变量不生效，换后端地址要重建镜像。
4. **镜像体积**：默认 `INSTALL_LOCAL_EMBED=true` 会带上 torch，几百 MB 起；
   不用本地 embedding 时用 `--build-arg INSTALL_LOCAL_EMBED=false`。
5. **CI 的 docker job 不跑 `up`**：只验 `compose config` + `build --check` + 真构建两个镜像。
   要验端到端起栈，本地跑 `scripts/ci.py --stage container`。
6. **`ty` 未接入**：31 条诊断先清再接，见 §3。
7. **`uv build` 在本机会话里的缓存坑**：当 uv 输出接管道（`scripts/ci.py` 里就是这样）时，
   `uv build` 报 `Failed to initialize cache … 拒绝访问 (os error 5)`，手动在终端跑却成功。
   属主机环境问题，不是项目缺陷：`ci.py` 的 `build` 阶段给这一步单独钉了
   `UV_CACHE_DIR`/`TMP`/`TEMP` 到 `.tmp_ref/`，两种调用方式行为一致。
