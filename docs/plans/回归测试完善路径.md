### 0.3 本地取证：回归测试现状（事实，非印象）

取证命令与结果（`E:\projects\pyknora`，2026-11-02）：

1. **提交门禁只跑三件事，且不含数据库**
   - `scripts/ci.py` 是**生成文件**（`:3` 自述 `Generated by python-toolchain / py-ci-run`），门禁定义写在 `:32-100` 的 `PAYLOAD` JSON 里。它定义 **2 个 stage**：`lint`（`scripts/ci.py:36-76`）与 `test`（`scripts/ci.py:78-97`）；stage 之下才是 **step**：`ruff-check`（`scripts/ci.py:54`）、`ruff-format`（`scripts/ci.py:71`）、`pytest`（`scripts/ci.py:92`，命令 `uv run pytest -q tests/unit`）。
   - `security` 是**已存在的第 3 个 stage**（`scripts/ci.py:107-125`，内容是 pip-audit），它进 `ALL_STAGES`（`:127`）但**故意不进 `all`**：`_select` 在 `:147-150` 只把 `all` 展开到 `PAYLOAD.stages`，注释写明「security 必须显式点名」——理由是 pip-audit 要联网比对 OSV（`:105-106`）。
   - `.githooks/pre-commit` 只负责调度 `uv run python scripts/ci.py --stage all`，自身不定义任何检查。
   - 结论：**每次提交只验证"不需要数据库的那部分"**，`tests/api`（143 个用例）与 `tests/integration`（75 个）不在任何自动门禁里。

2. **用例规模与分布**（按 `^\s*(async )?def test_` 逐文件计数）

   | 目录 | 文件数 | 用例数 | 是否需要真 PG |
   | --- | --- | --- | --- |
   | `tests/unit` | 28 | 369 | 否 |
   | `tests/contract` | 3 | 5 | 否 |
   | `tests/api` | 16 | 143 | 是（ASGI + 真库） |
   | `tests/integration` | 13 | 75 | 是（每例 TRUNCATE） |

3. **"回归"这个概念在仓库里几乎不存在**
   - `src/**`、`scripts/*.py`、`tests/**` 里 `regression|回归` 合计仅 **11** 处命中（按三个目录全部 `*.py` 计数；多为注释措辞，无任何基线保存/对比机制）`[实测]`（`pyproject.toml:44-48`）。
   - 没有任何"上一次绿的结果"被保存、比较或作为门槛：`pyproject.toml:44-48` 的 pytest 配置只有 `testpaths`、`asyncio_mode = "auto"`、`addopts = "-q"`，无覆盖率门槛、无失败重跑、无基线文件。

4. **多进程共用测试库会造成假失败（已在会话中实测）**
   - 同时跑着 API/Worker 时执行 `pytest -q tests/api` 会出 `DBAPIError`；单跑同一用例 → `1 passed`。
   - 根因是 `tests/integration` 的 `TRUNCATE ... CASCADE` 需要 `ACCESS EXCLUSIVE`，与 Worker 的 `FOR UPDATE SKIP LOCKED` 争锁。
   - 结论：**"回归失败"目前无法自证是本轮改动引入还是环境冲突**——这是回归体系必须先解决的问题。

## 1 业务叙事：为什么"回归测试"是这套系统最薄的一环

PyKnora 的测试不是没有，而是**没有"回归"这个概念**：517 条用例能跑 `[实测]`（`scripts/ci.py:92`），但本次未核到任何机制回答"这次改动比上次差在哪"。三条事实支撑这个判断：

1. 自动门禁只跑 `tests/unit`（`scripts/ci.py:92` 的命令是 `uv run pytest -q tests/unit`），而 **218 个需要真库的用例（37%）** 不在任何自动门禁里 —— 它们只在人想起来时跑。
2. 全仓 `regression|回归` 只有 **11** 处命中，`pyproject.toml:44-48` 没有覆盖率门槛、没有基线文件、没有 junit 归档 —— 跑完就散，第二次跑无从对比。
3. 一次全量跑（**112.25 s**）的结果是 `517 passed, 8 failed, 222 errors`，其中 222 个 error 的真因是 `password authentication failed for user "postgres"` —— 连错了库。**环境问题长得和"全盘崩了"一模一样**，这就是"心里没底"的具体形状：不是怕代码坏，是怕看到红色也判断不出到底是不是自己改坏的。

所以本文档要补的不是"再多写点用例"，而是三道机制：**能重复跑（环境自愈）→ 能对比（基线）→ 能拦住（门禁）**。

### 2.5 门禁 3 产出物：需求规格（裁决后的口径）

**做什么**
1. 一次性 PG 容器 + 不经 docker 的迁移执行器，让 `tests/api`/`tests/integration` 不依赖机器上哪个容器在跑（S1）。
2. 四个 marker（`smoke`/`full`/`security`/`needs_db`）与 `scripts/ci.py` 的两个新 stage：`smoke`（`pytest -q -m smoke`）与 **`guard`**（`pytest -q -m security`）。**新 stage 不能叫 `security`**——那个 id 已被 pip-audit 占用（`scripts/ci.py:107-125`），重名会让 `_select` 的 `by_id`（`:152`）静默覆盖成其中一个（S2）。
3. `scripts/regression.py run/compare`：junitxml 归档 + 四类差异逐条报 ID（S3）。
4. 7 个安全用例文件的 `pytestmark`，以及由 OpenAPI 驱动的"未授权必须 401/403"矩阵（S4、S5）。
5. `guard` stage 红即整次失败（一票否决，C4）；但它**是否进 `all` 需要裁决**——见 S6 与 §9 第 9 条：进 `all` 才能拦住提交，可是 `guard` 里多数用例要真库，会让提交钩子从 10 s 量级变成"必须起 Docker"（S6）。
6. `--testmon` 作为本地加速（可选，S7）；README 增一节并做一次从零演练（S8）。

**明确不做什么**
- ❌ 不接远端 CI（GitHub Actions / Jenkins）：本方案只在本地门禁与手动 full 跑。
- ❌ 不设覆盖率门槛：用户没要求，且会引入"为了数字改测试"的噪声；覆盖率只作为观察项（可选打印）。
- ❌ 不做 flaky 趋势库、不做历史曲线、不做评测集（那是已存在的另一条线，且用户明确要求本次不参考它）。
- ❌ 不改任何既有断言、错误码语义、迁移文件、`v_active_chunks` 视图。
- ❌ 不用 `pytest-xdist` 并行：TRUNCATE + 一次性容器在 Windows 上并行会放大锁竞争（`tests/integration/conftest.py:47-55` 的注释已写明这个教训）。

**验收标准**（每条都必须有可观察证据，见第 8 节）
| # | 标准 | 证据形态 |
| --- | --- | --- |
| V1 | 不手动起库时 `tests/api` 能跑 | 一条 `uv run pytest -q tests/api/test_api_knowledge_bases.py` 的真实输出 |
| V2 | 分层计数自洽 | `-m smoke`/`-m needs_db` 两次 `--collect-only` 的数字 |
| V3 | 基线能分辨四类差异 | 人为改坏一条再改回的 `compare` 输出 |
| V4 | 安全类单独可跑 | `-m security --collect-only` 计数 |
| V5 | 未授权矩阵能失败 | 注释掉一个鉴权依赖后的失败输出 |
| V6 | 一票否决生效 | `--stage all` 在 security 红时的退出码与本行文案 |

**约束与前提**
- 前提：本机有 Docker 且能拉 `pgvector/pgvector:pg16`（已确认本仓库的镜像约定是 pg16 + pgvector）；Docker 不可用时全链路必须 skip 而不是 fail。

## 4 契约（可被断言的部分）

| 编号 | 契约内容 |
| --- | --- |
| C1 | **环境契约**：`tests/api` 与 `tests/integration` 不得依赖机器上"哪个容器在跑"；库地址只能来自 ①一次性容器 fixture，或 ②`PYKNORA_TEST_DATABASE_URL`。二者都拿不到时**必须 skip 并说明原因**，不得 fail。 |
| C2 | **分层契约**：`pytest -m smoke` 必须不连库（unit + contract）；`pytest -m full` = 全部；`pytest -m security` 必须只含标记为安全的用例。 |
| C3 | **基线契约**：每次回归产出 `junitxml`；比较结果必须能报出四类差异（新增失败 / 消失的失败 / 由绿转红 / 用例消失），四类**逐条列 ID**，不允许只报计数。 |
| C4 | **一票否决契约**：`security` stage 红 = 整次回归失败，**即使其它 stage 全绿**；反向不成立（security 绿不能掩盖 smoke 红）。 |
| C5 | **未授权契约**：全部带鉴权依赖的端点，请求里不带 `Authorization` 时必须回 401/403；白名单只有 `/health`、`/openapi.json`、`/docs*`、`/static/*`、`/auth/register`、`/auth/login`。新增端点若不在白名单且请求不带令牌能 200，视为回归失败。 |
| C6 | **不变更契约**：本方案不改任何既有断言、不改错误码语义、不改 `v_active_chunks`；只加 fixture、marker、脚本与文档。 |

### S1 环境自愈：一次性 PG + 不经 docker 的迁移（TDD 模式）

**做什么**：新增 `tests/support/pg_container.py`：`postgres_container()` 用 `PostgresContainer(image="pgvector/pgvector:pg16", username="postgres", password="dev", dbname="pyknora")`；`apply_migrations(url)` 读 `migrations/*.sql`，去掉 `\` 开头的 psql meta 行、把 `:dim` 替换成 `settings.embedding_dim`，再用 asyncpg 整段 `execute`。在 `tests/conftest.py` 里做 session 级 fixture：起容器 → 迁移 → **`settings.database_url = url` 且 `dispose_engine()`**（`src/pyknora/db/session.py:25-34` 是惰性单例，改了 settings 必须先 dispose 才会重建）→ 用完销毁。

**指令模板**（可直接复制给执行者）：

### S3 基线：junitxml + 四类差异（TDD 模式）

**做什么**：`scripts/regression.py`：`run --label <name>` 调 pytest（`--junitxml=.regression/<label>.xml -p no:cacheprovider`）；`compare --base <a> --target <b>` 解析两份 junit，输出四类差异并给出退出码（target 出现"新增失败"或"由绿转红"→ 1；否则 0）。基线建议提交的是**摘要 json**（用例 id → 结果），xml 本体不入库。

**指令模板**：
```
实现 scripts/regression.py，只用标准库（xml.etree + argparse + json）：
run 子命令：subprocess 调 uv run pytest --junitxml=...，透传 -m/-k
compare 子命令：读两份 xml → {testid: outcome(passed/failed/error/skipped)} → 输出
  new_failures（target 红 & base 绿）、fixed（target 绿 & base 红）、still_failing（两边都红）、disappeared（base 有 target 无）
每条都列 testid，不只列计数；compare 有 new_failures 时 exit 1
不要：不要引入 pytest-html、不要写数据库、不要动 .gitignore 之外的目录。
```

**通过信号**：`uv run python scripts/regression.py run --label base && uv run python scripts/regression.py compare --base .regression/base.json --target .regression/base.json` → 四类全 0、exit 0；人为把一条用例断言改错后再跑 `compare` → `new_failures` 恰好列出那一条、exit 1；把该用例改回 → `fixed` 列出同一条。

**翻车信号**：① 同一份文件对比出现大量 `disappeared` → junit 里 testid 含参数化随机值，需要归一；② 全是 `new_failures` → base 生成时用了不同 `-m` 选择；③ 解析不到 outcome → junit 版本/编码问题（spec 有 `classname`+`name`，必须拼成稳定 id）。

**来源**：`scripts/ci.py:92`
