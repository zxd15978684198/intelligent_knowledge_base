### 重复性：同一张图重复跑，波动 3.8 倍

为了判断 33 s 是内容问题还是机器噪声，对同一批 PNG 重复采样，共 **16 次单页识别**：

| 样本 | 各次耗时（秒） |
| --- | --- |
| 扫描件 p1（同图） | 19.07 → 10.94 → 12.50 → 20.32（子进程内） |
| A4 p1（同图，42 框） | 17.74 → 11.00 → 7.32 → 8.74（子进程内） |
| A4 p3（同图，28 框） | 33.37 → 35.03 → 17.63 → 14.21 → 9.12 |

汇总 16 个样本：**min 7.32 s · median 13.62 s · mean 16.30 s · max 35.03 s**；`>20 s` 占 **3/16 = 18.75%**，`>30 s` 占 **2/16 = 12.5%**。

- 首次出现（19.07 / 19.27 / 17.74 / 33.37）系统性偏慢，后续下降 → 存在明显的**暖机/热衰减**。
- **框数不能解释**：28 框的 A4 p3 反复跑出 33–35 s，42 框的 A4 p1 只要 7.3–17.7 s；同一张 A4 p3 在 5 分钟内跑出 33.4 / 35.0 / 17.6 / 14.2 / 9.1，证明是**机器侧噪声**而非算法对内容的敏感。
- 根因未定位（已排除文本框数量）。可疑项但未取证：笔记本 CPU 频率/温度墙、Windows Defender 实时扫描、onnxruntime 线程竞争（子进程内 26 个线程跑在 8 个逻辑核上）。

## 子进程开销

方式：`concurrent.futures.ProcessPoolExecutor(max_workers=1)`；先 `submit(whoami)` 在**父进程**拿到子进程 pid，再让子进程构造引擎并识别 1 页；父进程用 `psutil.Process(child.pid).memory_info().rss` 每 20 ms 采样，子进程在每个阶段写时间戳标记（`time.time()`）以对齐阶段。

两次独立运行：

| 指标 | 运行 1（扫描件 p1，24 框） | 运行 2（A4 p1，42 框） |
| --- | --- | --- |
| 池创建 → 拿到子进程 pid | 0.293 s | — |
| 子进程内 `import rapidocr_onnxruntime` | 1.704 s | — |
| 子进程内构造 `RapidOCR()` | **7.554 s** | **0.993 s** |
| 子进程内单页识别 | **20.324 s** | **8.744 s** |
| **子进程峰值 RSS（父进程采样）** | **398.9 MB** | **444.1 MB** |
| 峰值出现时刻（拿到 pid 后） | 14.32 s | — |
| 识别结束后 RSS | 56.6 MB | 98.6 MB（6 s 内稳定不降） |
| 关闭池前 RSS | 47.1 MB | 76.8 MB |
| 子进程线程数 | 26 | — |
| 父进程自身 RSS | 18.8 MB | 19.0 MB |

阶段 → 峰值 RSS（运行 1，按时间戳切分父进程采样）：

| 阶段 | 阶段内峰值 RSS |
| --- | --- |
| 子进程刚起（`child_start`） | 25.8 MB |
| 导入 rapidocr 后 | 63.3 MB |
| 构造引擎完成（`engine_ready`） | 104.4 MB |
| **识别阶段（含 rec 高峰）** | **398.9 MB** |
| 识别结束 | 56.6 MB |
| 空闲 1 s | 60.1 MB |

同进程内（非子进程）的对照：

| 点位 | RSS |
| --- | --- |
| 裸解释器 + psutil | 26.3–58.8 MB |
| 导入 rapidocr | 63.2–64.3 MB |
| 构造引擎后 | 93.1–98.5 MB（构造期峰值 104.7 MB） |
| **识别期峰值（整进程）** | **569.8 MB** |
| 识别结束（Working Set 被回收） | 25.7–51.8 MB |

要点：**峰值是稳态的 5–8 倍，且峰值只出现在 rec 阶段**；识别结束后 Windows 会把 Working Set 大幅回收（97 MB → 26–57 MB），所以「常驻内存」和「峰值内存」是两个数量级不同的数，做容量规划必须用峰值。

## 结论（回答上面三个问题）

**1）引擎首帧加载几秒、常驻内存多少 MB？**

- 首帧 = 解释器导入（0.76–1.70 s）+ 构造 `RapidOCR()` + 第一次推理。
- 构造耗时实测 **0.98 / 0.99 / 0.99 / 1.05 s（稳态）· 2.62 s（进程首次冷跑）· 7.55 s（新 spawn 的子进程，单次观测）**。取**「约 1 s 稳态，冷进程 1–8 s」**，容量规划按 **8 s** 留余量。
- 常驻内存：**稳态 50–100 MB**（两次子进程分别停在 56.6 / 98.6 MB，6 s 内不降）；**识别期峰值 399–444 MB（子进程）/ 570 MB（同进程整进程）**。模型 15.44 MB 常驻可忽略，大头是 rec 阶段的中间张量。
- 首帧完整链路（子进程冷起 → 出第 1 页结果）实测 **30.9 s**（1.70 导入 + 7.55 构造 + 20.32 识别 + 开销）。

**2）单页识别最慢多少秒（D10-2 的按页预算 20 s 够不够）？**

- **最慢 35.03 s，中位 13.62 s，16 次里 3 次 > 20 s（18.75%）、2 次 > 30 s（12.5%）。**
- **20 s 不够。** 在这台 i5-9300H 笔记本上按 20 s 设页级超时，会把约 1/5 的正常页误判成超时并降级。
- 建议：页级预算改为 **≥45 s**（20 s 预算的 2.25 倍，覆盖实测 35 s 峰值 + 首帧 8 s 余量），或保留 20 s 但**把超时当「慢」而非「失败」**——降级成只回「该页为扫描件，OCR 超时」而不是报错整单失败，并在 job 上记 `ocr_slow` 指标。
- 另注意：慢的是 rec 阶段，而 rec 与页内文本框面积相关；扫描件 24 框就要 19 s，A4 表格页 28 框能到 35 s。**不能按框数估时**。

**3）常驻子进程方案在本机（8 GB 内存）是否可行？**

- **可行，但只能常驻 1 个，且不能按峰值 ×N 并发。**
- 数值：常驻稳态 50–100 MB（占 8 GB 的 1.2%），识别期峰值 400–570 MB（占 5%–7%）。单个 OCR worker 完全吃得下。
- 风险线在并发：`max_workers=2` 在极端情况下峰值可叠加到 ~0.8–1.1 GB；再叠加 API/Worker/PG 客户端与本机其他进程，8 GB 机器上**不建议 OCR 并发 >1**。与 ADR 里「`ProcessPoolExecutor(max_workers=1)` 常驻」的口径一致——这条选择被本次实测支持。
- 附带成本：Windows 上 `ProcessPoolExecutor` 用 spawn，池创建到可用 0.29 s、子进程导入 1.7 s；**进程一旦被回收/重建，就要重付一次「冷首帧」**（本机实测最坏 7.55 s 构造 + 35 s 首页）。所以「常驻」是性能前提，不是优化项。

## 局限与未验证

1. **样本不足**：桌面 26 个 PDF 里只有 1 份真扫描件（2 页，另一个目录是同文件的副本），**没有 ≥5 页的扫描件**，多页长文档的耗时/内存累积趋势未覆盖。所有「扫描件」结论只基于这 2 页。
2. **A4 辅样本偏乐观**：它本身有文本层，是「渲染成图再 OCR」，无扫描噪声、无歪斜、无低对比度。真实扫描件的 det 耗时可能更高。
3. **未定位 33–35 s 尾延迟根因**：已排除框数因素，但未做 CPU 频率/温度、Defender、ORT 线程数的对照实验。因此给出的是「观测上界」，不是可解释的性能模型。
4. **长空闲后的「再首帧」未测**：只观察到识别后 6 s 内 RSS 稳定（98.6 MB 不变）。Working Set 在更长时间空闲后是否被系统换出、下次调用是否重新付冷启动代价（这是常驻进程最关心的项），**未验证**，需 ≥10 分钟空转后复测。
5. **未测并发**：`max_workers=2/4` 的总内存与吞吐、以及两个 OCR 争抢 4 核 8 线程时的单页耗时劣化倍数，都未测。
6. **平台绑定**：全部数据来自 Windows 10 + spawn 语义。若生产在 Linux 容器（fork + 更少核配额），启动成本、线程数、内存计量口径都会不同，**需在部署镜像内重测**，不能直接沿用本表。
7. **内存计量口径**：用 `psutil` 的 `rss`（Windows Working Set），**不是** private bytes / commit charge。Windows 会把可回收页从 Working Set 里摘掉，所以「稳态 26 MB」这类数字偏低，不代表进程真的只占 26 MB 私有内存。
8. **未做的开关与分辨率**：未测 `use_det/use_cls/use_angle` 组合、未测 300dpi（D10 定的是 200dpi，这里只验证了 200dpi）、未测 PDF 加密/损坏/超长页。
9. **未触及 VLM 通道**：D10 的「VLM 认结构」分支完全没测，本节点只覆盖 OCR 认字。
10. 本报告**未**改动 `src/`、`tests/`、`pyproject.toml`、`uv.lock`，也未执行任何 git 命令；脚本均落在系统临时目录（`%TEMP%`）。
