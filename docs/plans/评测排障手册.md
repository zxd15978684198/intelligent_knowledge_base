## 2. 故障一：检索为空

### 2.1 最小字段表

| 字段（逐字对齐契约） | 期望值 | 异常值含义 |
| --- | --- | --- |
| `retrieval_completed.retrieval_count` | `> 0` | `= 0` 即本故障；**`0` 与 `null` 不同**，`null` 是没测出来，不许当 0 读 |
| `retrieval_completed.stage` | `"retrieve"` | 不是 `"retrieve"` 说明事件记错阶段，判据失效 |
| `retrieval_completed.outcome` | `"ok"` | `"empty"` = 无命中；`"error"` = 抛异常，此时看 `error_type`，不看 `retrieval_count` |
| `retrieval_completed.error_type` | `null` | `no_permission` / `index_missing` / `filtered_out` / `no_evidence`，判定顺序见 §2.2 |
| `retrieval_completed.duration_ms` | 与 `stage_timings.retrieval_ms` 同量级 | 差一个数量级 = 计时点挂错位置 |
| `query_http_status`（raw 已有） | `200` | `404` + `error_code=RESOURCE_NOT_FOUND` → 权限问题，不是检索问题 |
| `degraded`（raw 已有） | `{}` | 非空 = 单路失败后只剩一路，空结果可能是「一路挂了」而非「库里没有」 |

### 2.2 判定顺序（不可颠倒，前三步都是排除法）

1. **`no_permission`**——先排除权限。看 `query_http_status`：`404` 说明在 handler 之前就被
   `require_kb_access`（`src/pyknora/api/deps.py:156`，FastAPI 依赖）挡掉，**`retrieval_completed` 根本不会发出**。
   先看 HTTP 码再看事件，顺序反了会把 404 误读成「检索为空」。
2. **`index_missing`**——查 `v_active_chunks` 该 build 是否有行。视图（`migrations/0014_chunk_locator.sql:47`）按
   `kb_id / build_id / index_version` 组织；该 build 一行都没有 = 索引侧没写成功，与检索无关。
3. **`filtered_out`**——查过滤谓词。候选池有行、最终 `hits` 为空，典型是 `scope` 过滤（跨工作区）
   或 `index_version` 不等于当前激活版本；同时看 `degraded` 是否非空。
   **注意**：`services/retrieval/search.py:321` 的标签规则是「RRF 之后候选池非空才敢叫 `filtered_out`」，
   而当前 RRF 不会把非空池清空，所以这个标签**实际拿不到**——真看到 `filtered_out`，先怀疑
   `search_hybrid` 被人加了打分阈值，而不是去查 ACL。
4. **`no_evidence`**——前三者都排除，才允许判「语料真无答案」。此结论必须能指出哪份语料缺这段话，
   否则退回第 3 步重查。

## 3. 故障二：回答错误但检索正常

### 3.1 最小字段表

| 字段（逐字对齐契约） | 期望值 | 异常值含义 |
| --- | --- | --- |
| `retrieval_completed.retrieval_count` | 与 `prompt_built.retrieval_count` **相等** | 不等 = 两条事件不是同一次检索（串号或漏记） |
| `prompt_built.evidence_count` | 等于 `retrieval_count` | 小于 = 被上下文预算 `chat_max_context_chunks` 截掉，**差值就是丢掉的条数** |
| `prompt_built.prompt_version` | 等于 `PROMPT_VERSION`（当前 `pyknora-rag-v1`） | 不同 = 这轮换了提示词，跨轮比较作废 |
| `chat_finished.token_usage.prompt` | `> 0` | `= 0` 且 `evidence_count > 0` = 资料没进 prompt（拼接漏了） |
| `results[].document_id`（raw 已有，**不是 `source_id`**） | 含黄金 `document_id` | 不含 = 检索没把黄金来源排进来，属检索侧 |
| `gold_document_ids`（raw 已有） | 非空 | 空 = 无黄金来源，本判据不适用 |
| `invalid_citations`（raw 已有） | `0` | `> 0` = 引用了被截掉或不存在的资料，幻觉硬信号 |

### 3.2 判定顺序（前一步不过不进下一步）

1. **上下文截断**：`retrieval_count - evidence_count = 被截条数`。差值 `> 0` 时先解释它
   （预算小 / 单条 chunk 太长），**不要在生成侧找原因**。
2. **黄金来源未进候选**：查 `gold_document_ids` 是否出现在 `results[].document_id`。
   口径注意：`results` 是 `/query` 侧 `top_k=5`，`citations` 是 `/chat` 侧 `chat_top_k=6`，
   两者不是同一路，**不能互相替代**。不在 → 检索/排序问题，不是生成问题。
3. **生成侧**：前两步都正常仍答错，才看 `prompt_version`（是否与基线同版）与
   `summary.json` 的 `config.chat_model`（是否换模型）。任一不同，跨轮比较直接作废。

## 4. 故障三：SSE 卡住

### 4.1 最小字段表

| 字段 | 期望值 | 异常值含义 |
| --- | --- | --- |
| `first_token.first_token_ms` | 存在且 `> 0` | 缺失 = 模型未吐字（建流前失败或上游超时） |
| `chat_finished.outcome` | `"completed"` | `"timeout"` / `"error"` 直接指认终止原因 |
| `chat_finished.error_type` | `null` | 非 `null` 必须与 `outcome=error` 同时出现，只出一个说明记错 |
| `chat_finished.stage_timings` 四段之和 | 与 `total_ms` 差 `< 5%` | 差得远 = 某段漏记（大概率 `model_ttft_ms`），四段不可信 |
| SSE `done` 事件次数 | **恰好 1** | `0` = 未收尾（前端一直转圈）；`2` = 双终态，违反 Day4 §10.4 |
| SSE `done.status` | `COMPLETED` | `ABSTAINED`（门控拒答，正常）/ `TIMEOUT` / `FAILED` |
| SSE `done.run_id` | 与日志 `run_id` 同值 | 不同 = 串流 |
| 响应头 `X-Request-ID` | 32 位 hex | 缺失 = 中间件未生效，无法与日志对齐 |

### 4.2 四种组合各对应什么故障

判据顺序：**先看 HTTP 码**（决定流有没有开）→ `first_token` 有无 → `chat_finished` 有无 → 数 `done`。

| `first_token` | `chat_finished` | `done` 次数 | 故障 | 下一步 |
| --- | --- | --- | --- | --- |
| 无 | 无 | 0，HTTP **503** | **建流前 503** | `DEPENDENCY_UNAVAILABLE`：embedder 未注入（`api/v1/chat.py:161`）或 chat model 未配置（`:167`）。这是**设计内**行为，查部署配置，不查检索 |
| 无 | 有（`outcome=timeout`） | 1，`status=TIMEOUT` | **上游超时** | 超时被 `asyncio.wait_for` 罩在 `anext` 上（`chat.py:416`，`except TimeoutError` 在 `:421`），事后补一只中文 token + `done(TIMEOUT)`（`:396`）。看 `stage_timings.model_ttft_ms` 与 `chat_timeout_s` |
| 有 | 无 | 0 | **生成器异常未降级** | 流已开、状态码改不了，异常穿出 → Starlette `response already started`（`answer.py:508` 的注释原话），客户端只见 `httpx.RemoteProtocolError`。正确做法见 `AGENTS.md` §8 第 9 条：`error` 事件（`chat.py:447`）+ 补 `done(FAILED)`（`:450`） |
| 有 | 有 | 1 | **前端断流**（服务端已收尾） | 服务端无责：查前端读超时、反代缓冲（`X-Accel-Buffering: no`，`chat.py:485`）、`Cache-Control` |

第五种要单独看一眼：`done` 出现 **2 次**——服务端双收尾缺陷，不是前端问题，按 Day4 §10.4 直接判失败。
