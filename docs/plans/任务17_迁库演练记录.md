## 2. 四步实测

### 2.1 导出

```powershell
$env:PYKNORA_DATABASE_URL='postgresql+asyncpg://postgres:dev@127.0.0.1:5434/pyknora'
uv run python scripts/export_metadata.py --out .tmp_migration/snapshot.json
```

产物：

| 文件 | 大小 | 说明 |
| --- | --- | --- |
| `.tmp_migration/snapshot.json` | 60 872 B | 给 `replay_metadata.py` 用（表 → 行列表，列名显式） |
| `.tmp_migration/snapshot.sql` | 53 494 B | 给人看 / 给 `psql` 用；`chunks` 的列清单**不含** `embedding`、`tsvector` |

导出表 8 张：`principals`、`workspaces`、`knowledge_bases`、`documents`、`document_versions`、`document_blobs`、`index_builds`、`chunks`。

### 2.2 重放

```powershell
$env:PYKNORA_DATABASE_URL='postgresql+asyncpg://postgres:dev@127.0.0.1:5434/pyknora_migrate'
uv run python scripts/replay_metadata.py --snapshot .tmp_migration/snapshot.json
```

结果：**5 个 KB / 7 个文档 / 31 个切片**，`embedding` 非空行数 **0**，`v_active_chunks` 为空。
（为空是正确现象：视图要求 `embedding IS NOT NULL`，而迁移刻意不搬向量。）

### 2.3 目标库重算向量（reindex）

```powershell
uv run python scripts/replay_metadata.py --snapshot .tmp_migration/snapshot.json
# 随后对每个存活 KB 触发:
# POST /api/v1/admin/reindex  {"kb_id": "...", "mode": "reindex"}
```

驱动脚本枚举**存活 KB**（`deleted_at IS NULL`）：`live kbs: 4, soft-deleted kbs skipped: 1`。

> 设计边界：`SqlKnowledgeBaseRepo.get` 过滤软删 KB，`get_embedding_profile` 因此取不到，已软删 KB 无法重算向量。
> 这是有意的——软删库不该分配算力，且其切片在目标库保持 `embedding IS NULL`，不会被任何读路径看见。

### 2.4 校验

```powershell
uv run python scripts/verify_migration.py `
  --source 'postgresql+asyncpg://postgres:dev@127.0.0.1:5434/pyknora' `
  --target 'postgresql+asyncpg://postgres:dev@127.0.0.1:5434/pyknora_migrate'
```

首次运行失败 2 项，定位后修正（见 §3），修正后输出：

```
OK   KB 集合一致（存活 4 / 软删 1）
OK   KB embedding profile 五字段一致
OK   documents 集合一致（7）
OK   活动 chunk 边界与正文一致（31）
OK   活跃 build 指针一致
OK   存活 KB 的活动 build 向量已重算（无 NULL）
OK   已软删 KB 的切片未搬向量（目标库保持 NULL）
OK   v_active_chunks 行数一致（源 0 / 目标 0）
结论：全部校验项一致
```

退出码 **0**。

## 3. 演练中发现并修正的问题

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 校验报 `v_active_chunks` 源 1 / 目标 0、且"缺向量 1 行" | 烟测库 `abb4f0b2-…` 在源库**已软删**，但 `v_active_chunks` 视图**不 join `knowledge_bases`**，只看 `documents.deleted_at`，于是源库仍露出 1 条幽灵行 | 校验器的 `_ACTIVE_CHUNK_COUNT_SQL` 显式 `JOIN knowledge_bases … AND k.deleted_at IS NULL`，与"存活 KB"口径对齐；另加断言"已软删 KB 的切片未搬向量"（`_ALL_NULL_VECTOR_SQL`），把这条边界写进契约 |
| 2 | 软删 KB 触发 reindex 报 `knowledge base embedding profile not found` | repo 有意过滤软删 KB | 驱动脚本枚举存活 KB，打印 `soft-deleted kbs skipped`；不视为失败 |

> 教训：视图 `v_active_chunks` 的可见性只覆盖到 `documents` 层，**KB 层软删不在视图里**。读端口若只依赖视图，就要自己补 KB 存活谓词。
